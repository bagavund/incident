# Системный анализ IMS (Incident Management System)

> Версия анализа: 2026-09-05
> Часть I — для бизнеса и продукта. Часть II — для инженеров.
> Статус проекта: фронтенд и бэкенд соединены и работают на реальных данных, не прототип на моках.

---

## Часть I — для бизнеса и продукта

### 1. Проблема: инциденты жили в Excel

До IMS дежурные и инженеры фиксировали каждый инцидент вручную — в общей Excel-таблице на сетевом диске или в облаке. Формат таблицы работает, пока инцидентов немного и вопросы к данным простые. На практике оба условия быстро перестают выполняться.

> Таблица одинаково хорошо принимает и «14:32», и «14.32», и «около половины третьего» — и одинаково плохо превращается в отчёт для руководства.

Конкретные проблемы такого учёта:

- **Неструктурированный ввод.** Нет формы и обязательных полей — тип инцидента, критичность, зона ответственности каждый раз вписываются от руки, поэтому в одной колонке соседствуют «Backend», «бэк», «backend-команда» — это уже три разных значения для аналитики.
- **Метрики считаются вручную.** Чтобы получить среднее время реакции или долю нарушений SLA, нужно вручную писать формулы над датами, вставленными как текст — при малейшей ошибке в формате ячейка просто не считается, и это часто остаётся незамеченным.
- **Постмортем нигде не живёт целиком.** Хронология событий, эскалации (кому звонили и сколько раз) и итоговая причина оказываются в разных вкладках или вообще не фиксируются, если у инженера не было времени.
- **Нет ролей и истории изменений.** Любой с доступом к файлу может стереть строку; кто и когда это сделал — не восстановить.
- **Аналитика — это отдельная разовая работа.** «Сколько инцидентов было у сервиса X за квартал и какая доля — по вине внешнего провайдера» превращается в ручную выгрузку и фильтрацию, а не в клик по дашборду.

**Симптом, а не гипотеза:** каждый новый разрез отчётности (по зоне, по времени суток, по каналу эскалации) в табличном учёте — это новая ручная выгрузка. В IMS это одно и то же представление, которое просто обновляется само.

### 2. Что делает IMS

IMS — веб-реестр инцидентов с формой ввода, автоматическим расчётом метрик и живым дашбордом. Он не переизобретает процесс работы с инцидентом — он даёт этому процессу структуру.

**Регистрация инцидента**
- Форма с обязательными полями: название, сервис(ы), тип, критичность, дежурный, время начала — инцидент нельзя опубликовать с пропущенными базовыми данными.
- Один инцидент может затрагивать несколько сервисов одновременно — это норма для реальных сбоев, а не исключение.
- Черновик: если постмортем не готов (нет причины), инцидент сохраняется как черновик и помечается в списке — не нужно придумывать данные, чтобы просто не потерять запись.

**Постмортем**
- Хронология по шагам («обнаружено» → «диагностика» → «передано ответственным» → опционально «информирование» / «war room» → «решена») с возможностью вставлять промежуточные шаги.
- Журнал эскалаций: кому звонили, каким каналом, сколько попыток потребовалось и с каким результатом.
- Заглушка (временное решение) фиксируется отдельно — когда установлена и когда снята.

**Аналитика без ручной сборки**
- Ключевые показатели за период с сравнением к предыдущему: количество инцидентов, среднее время реакции, среднее время решения, доля соблюдённого SLA.
- Тепловая карта «день недели × час» — видно, когда система рвётся чаще всего.
- Разбивка по зонам ответственности, по типу инцидента, топ проблемных сервисов.
- Показатели по эскалациям: доля «не дозвонился с первого раза», доля инцидентов ночью/в выходные, как часто собирают war room.
- Клик по любому графику — переход к списку инцидентов, из которых он собран.

**Управление справочниками — без разработчика.** Список сервисов, зон ответственности, типов инцидентов и уровней критичности редактируется прямо в интерфейсе (раздел «Администрирование»): добавить значение, переименовать, удалить. Удаление заблокировано, пока значением пользуется хотя бы один инцидент — так справочник не рассыпается из-за случайного клика.

### 3. Ценность для бизнеса

| Показатель | Значение |
|---|---|
| Кликов от вопроса руководителя до цифры | 2 — открыть дашборд и выбрать период |
| Форм для одного инцидента | 1 — вместо разрозненных вкладок под причину, хронологию и эскалации |
| Строк кода, чтобы добавить сервис/зону/тип | 0 — это делает дежурный через интерфейс |
| Ролей доступа | 2 — инженер пишет и редактирует, наблюдатель только читает |

- **Руководству** — актуальная картина надёжности по требованию, а не по расписанию ручных отчётов; видно, какие сервисы и зоны требуют внимания в первую очередь.
- **Дежурным и инженерам** — меньше рутины на оформление, один привычный процесс вместо «как договорились в этот раз».
- **Для решений об инвестициях** — куда вкладываться в надёжность в первую очередь, на основании частоты инцидентов и MTTR по сервису, а не по ощущениям.
- **Для роста** — справочники и роли уже готовы к тому, чтобы завтра сервисом пользовалась ещё одна команда, без переписывания кода под каждую.

### 4. Было / стало

| Excel-таблица | IMS |
|---|---|
| Свободный текст в ячейках — «Backend», «бэк», «backend-команда» уживаются рядом | Единый управляемый справочник зон/типов/критичности, дубли отклоняются при вводе |
| Метрики — ручные формулы над датами-текстом, которые легко сломать | MTTD, MTTR и SLA считаются автоматически по каждому инциденту и по периоду |
| Хронология и эскалации — в разных вкладках или в свободных комментариях | Структурированная хронология и журнал эскалаций внутри одной карточки инцидента |
| Любой с доступом к файлу может стереть или исказить строку без следа | Черновики, роли доступа, удаление с явным подтверждением |
| Новый разрез отчёта — это новая ручная выгрузка и фильтрация | Дашборд и тепловая карта обновляются сами; клик по графику — переход к деталям |

### 5. Текущий статус и ближайшие шаги

Фронтенд и бэкенд соединены и работают на реальных данных. Дальше — три направления, которые уже обозначены, но требуют решений не только инженерных:

| Статус | Направление |
|---|---|
| 🔴 Заблокировано | **Единая корпоративная авторизация (SSO)** — точка входа для неё уже выделена в коде отдельным экраном; переход на неё не требует переписывать остальное приложение. Ждём токен от команды разработки SSO. |
| 🟡 Планируется | **Вынос раздела администрирования** на отдельный маршрут/поддомен — сейчас доступен только из меню «Настройки», не из основной навигации. |
| 🟡 Планируется | **Обобщение под другие команды** — требует отдельного решения о модели данных (общие инциденты или изолированные рабочие пространства на команду), прежде чем начинать разработку. |

## Часть II — для инженеров

### 1. Архитектура

Классический SPA поверх REST API, рассчитанный на деплой одним процессом на одной машине: сборка фронтенда кладётся прямо в публичную директорию Laravel, и один `php artisan serve` отдаёт и статику, и API.

```
[ React SPA ]  →  [ REST + JWT ]  →  [ Laravel 13 / PHP 8.3+ ]  →  [ SQLite ]
  React 18 + TS       JSON/HTTPS         Кастомный JWT              14 миграций
  Vite, код-сплит      Bearer-токен       (firebase/php-jwt)         Файл на диске
  Tailwind, Recharts   /api-прокси в dev  Eloquent ORM               Драйвер меняется
  Свой роутер          Общий origin       FormRequest-валидация      в .env без правок
  на History API       в проде            Ролевой middleware         схемы
```

**Почему один сервер.** Продуктовое требование — работать одной командой на одной ВМ. `npm run build` кладёт статику фронтенда в `backend/public`, Laravel отдаёт её через catch-all маршрут для всех путей, кроме `/api/*`. Это же убирает CORS в проде: всё на одном origin.

### 2. Модель данных

Ядро — таблица `incidents` со свободными строковыми полями `type` и `criticality`, которые сверяются со справочниками, но не жёстко привязаны внешним ключом — так справочник можно менять, не трогая уже сохранённые инциденты.

**`incidents`** (ядро)
- `id`, `code` (человекочитаемый, напр. `INC-2026-00001`)
- `title`, `type`, `criticality` — свободный текст
- `status`: enum `draft` / `published`
- `sla`: enum `met` / `breached`
- `on_duty_name`
- `started_at`, `detected_at`, `resolved_at`
- `stub_on`, `stub_off` — строки `"ЧЧ:ММ"`
- `cause`, `impact`, `task_link`
- `zones`, `custom_fields` — JSON

**`services`** — справочник (`id`, `name` unique), связь many-to-many через **`incident_service`** (pivot: `incident_id`, `service_id`)

**`zones`**, **`incident_types`**, **`criticalities`** — три одинаково устроенных справочника (`id`, `name` unique)

**`timeline_steps`** (1 → N к инциденту)
- `incident_id`, `position`
- `kind`: enum, 6 значений
- `action`, `time` (`"ЧЧ:ММ"`), `custom` (bool)

**`escalation_attempts`** (1 → N к инциденту)
- `incident_id`, `position`, `time`, `callee_name`
- `kind`, `channel`, `result` — enum'ы
- `attempts` — int

**`custom_field_definitions`** — `key`, `label`, `type`, `options` (JSON). *Не используется текущим UI.*

**`users`** — `role` (`engineer` / `viewer`), `name`, `email`, `position`

> **Технический долг.** `custom_field_definitions` и колонка `custom_fields` реализованы на бэкенде (валидация, аналитика по произвольному полю), но текущий UI конструктора кастомных полей на фронтенде убран при последнем редизайне формы. Инфраструктура жива и протестирована, просто не подключена к интерфейсу.

### 3. Ключевые алгоритмы

**Расчёт SLA по порогу критичности** — `src/data.ts · computeSla()`

Порог зависит от критичности инцидента и сравнивается с фактическим временем решения:

```
Критичный      → 60 минут
Важный         → 240 минут
Второстепенный → 1440 минут (сутки)

минуты(resolvedAt − startedAt) ≤ порог  →  «Соблюден»
иначе                                    →  «Нарушен»
```

**Метрики MTTD / MTTR из «голого» времени шага** — `IncidentMetrics`, `Duration::anchorTime()`

Шаги хронологии хранят только время суток («10:20»), без даты — дата инцидента не дублируется в каждом шаге. Чтобы посчитать разницу в минутах между «Диагностика» и «Передано ответственным», время шага сначала «привязывается» к календарной дате начала инцидента (`started_at`), и только потом считается разница между двумя получившимися отметками.

**Переход через полночь в форме хронологии** — `src/data.ts · validateTimelineOrder()`

Наивная проверка «каждый следующий шаг позже предыдущего» ломается, если инцидент начался поздно вечером, а следующий шаг зафиксирован за полночь. Валидатор ведёт накопительный сдвиг по суткам: если новое время меньше предыдущего и предыдущее было не раньше 20:00, а новое — не позже 08:00, это считается переходом на следующие сутки, а не ошибкой оператора.

**Регистронезависимая проверка дублей в справочниках** — `LookupController::findByName()`

Добавление и переименование значений в справочниках (сервисы, зоны, типы, критичность) не должно допускать «API Gateway» и «api gateway» как два разных значения.

> **Найдено при разработке:** SQL-функция `LOWER()` в SQLite приводит к нижнему регистру только ASCII-символы — кириллица не изменяется. Сравнение «Значение А» и «значение а» в SQL-запросе не совпадало. Сравнение перенесено в PHP (`mb_strtolower`), проблема воспроизведена тестом до того, как попала в эксплуатацию.

**Защита справочника от удаления «в живую»** — `LookupController::destroy()` + `Admin.tsx`

Удаление зоны/сервиса/типа/критичности блокируется, если хотя бы один инцидент всё ещё на него ссылается. Проверка выполняется дважды осознанно: на клиенте — для мгновенной обратной связи (сообщение под списком без запроса на сервер), и на сервере — как источник истины (`409 Conflict`), на случай гонки или прямого обращения к API в обход интерфейса.

**Защита от потери несохранённых изменений** — `IncidentForm.tsx · dirtyRef`

Пока в форме есть несохранённые правки, переход по навигации внутри приложения и закрытие вкладки требуют подтверждения.

> **Найдено при разработке:** React `StrictMode` в dev-режиме дважды вызывает эффекты при монтировании. Реализация «пропустить первый запуск эффекта» на этом ломалась и помечала форму изменённой сразу при открытии — из-за чего сразу после успешного сохранения всплывал лишний диалог подтверждения. Флаг «изменено» переведён на сравнение со снимком исходных значений вместо счётчика запусков эффекта — результат не зависит от того, сколько раз эффект фактически выполнился.

### 5. Клиент: состояние, роутинг, границы ответственности

**Состояние — React Context поверх REST, без Redux.** Единый `StoreProvider` при монтировании тянет справочники и полный список инцидентов, дальше отдаёт наружу тот же интерфейс, что был у моков на localStorage. Экраны (дашборд, список, форма) написаны один раз против этого интерфейса и не знают, ходит ли он в сеть или читает из памяти — компонентам не потребовалось меняться при подключении к бэкенду.

**Аналитика считается на клиенте — сознательный выбор на сейчас.** Backend уже отдаёт частичный расчёт метрик через `/api/analytics/dashboard`, но дашборд фронтенда продолжает считать все графики сам — по полному списку инцидентов, полученному одним запросом. Причина: клиентские функции покрывают более широкий набор метрик (рецидивы, скорость канала связи, доля ночных/выходных инцидентов), чем сейчас есть на сервере. Перенос на серверный расчёт — отдельная задача, не блокирующая эксплуатацию при текущих объёмах данных.

**Роутинг без библиотек.** Самодельный роутер на History API (~30 строк): один `navigate()`, один `usePath()`. Экраны разбиты через `React.lazy` — открыть карточку инцидента не значит загрузить код графиков дашборда.

### 6. Тесты и качество

| Показатель | Значение |
|---|---|
| Тестов PHPUnit (backend) | 42 — все проходят |
| Миграций БД | 14 — полная история схемы |
| Маршрутов REST API | 36 |
| Замечаний Pint / TypeScript-компилятора | 0 |

Backend покрыт feature-тестами Laravel (создание/редактирование/удаление инцидента, права доступа по ролям, валидация, CRUD справочников, аналитика). Frontend проверяется вручную через Playwright по ключевым сценариям (навигация, форма, guard несохранённых изменений) — модульных тестов на фронте пока нет, это осознанный пробел, а не упущение.

### 7. Эксплуатация

**Локальная разработка (два процесса)**
1. Backend: `cd backend && php artisan serve` — поднимает API на `127.0.0.1:8000`.
2. Frontend: `npm run dev` — Vite сам проксирует запросы `/api/*` на backend, поэтому CORS настраивать не нужно.
3. Демо-доступ: `engineer@ims.local` / `password` (роль «инженер», может писать) и `viewer@ims.local` / `password` (только чтение).

**Продакшн (один процесс, одна ВМ)**
1. `npm run build` собирает фронтенд прямо в `backend/public`.
2. Laravel отдаёт статику и API из одного процесса — `php artisan serve` либо, при необходимости, полноценный веб-сервер (Nginx + PHP-FPM) перед тем же приложением.
3. SQLite подходит для текущего объёма данных; переход на MySQL/Postgres — это правка `DB_CONNECTION` в `.env` и прогон миграций, схема к драйверу не привязана.

> **Известные ограничения.** Мобильная адаптация вёрстки не входит в текущий объём работ (продукт используется с рабочего места). Авторизация — временное решение на собственном JWT до подключения единой корпоративной SSO. Раздел администрирования пока доступен только из меню «Настройки», отдельный маршрут для него не выделен.
